# 페어 조별 사진 번호 설계

## 목표

사진 증거의 `#번호`를 전역 번호가 아닌 현재 조와 페어 조가 함께 보는 수사 그룹 단위 번호로 부여한다. 관리자 전체 사진 초기화 후에는 모든 그룹의 다음 사진 번호가 `#1`이 된다.

## 범위와 동작

- 페어링이 없는 조는 자기 조만의 번호를 `#1`부터 사용한다.
- 1조와 4조가 페어이면 두 조가 올린 사진은 같은 번호 공간을 공유한다. 예를 들어 1조가 `#1`을 올린 뒤 4조가 올리면 `#2`가 된다.
- 다른 조 또는 다른 페어의 사진 번호는 독립적이며 각각 `#1`부터 시작한다.
- `/admin`의 `사진 전체 삭제`와 `전체 조 초기화`는 모든 사진 행, Storage 파일, 그룹별 번호 카운터를 제거한다.
- `/admin`의 조별 초기화는 번호 카운터를 초기화하지 않는다. 페어 상대의 기존 사진과 번호 연속성을 보존한다.

## 구현 방식

`photo_evidence`의 전역 sequence 기본값을 사용하지 않는다. 업로드 전에 현재 `game_state.pairings`를 읽어 두 조 중 사전순으로 앞선 조 번호를 안정적인 그룹 키로 계산한다. Supabase RPC가 이 그룹 키별 카운터를 원자적으로 증가시키고, 반환한 번호를 새 사진 행의 `evidence_number`에 저장한다.

새 `photo_evidence_counters` 테이블은 `group_key`를 기본 키로 하고 마지막으로 발급한 번호를 보관한다. RPC는 행 잠금 또는 UPSERT로 동시 업로드에도 중복 번호 없이 다음 값을 발급한다. 전체 초기화 흐름은 사진 삭제 뒤 이 카운터 테이블을 비워 다음 발급이 `#1`이 되게 한다.

## 오류 처리와 검증

- 번호 발급 RPC가 실패하면 이미지 업로드 후 사진 행을 만들지 않고 기존 업로드 실패 흐름으로 사용자에게 오류를 표시한다.
- 단위 테스트는 페어 그룹 키의 정규화와 페어/비페어 번호 공간 분리를 검증한다.
- Supabase SQL은 별도 마이그레이션 안내로 제공하며, 클라이언트 코드는 RPC와 명시적 번호 삽입만 사용한다.
